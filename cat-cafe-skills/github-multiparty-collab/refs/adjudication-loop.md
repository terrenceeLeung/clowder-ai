# 裁决-落地-验收环 Playbook

> 蒸馏自一次真实的四单位设计收敛风暴（一个 PR、17 条 comment、4 轮循环、零线下会议收敛）。
> 案例已脱敏：甲=发起方 writer C、乙=我方（writer A+B 兼 DRI）、丙=writer D。

## 环的定义（三层 ack 模型）

```
┌─ 意见方：表态（立场 + 逐项意见 + 锚定版本）
│    ↓
│  owner：落地（改自己的文档 + 报新版本 + 逐项对应说明 + 请求 re-ack）
│    ↓
│  意见方：验收（checkout 该版本 → 逐 diff 核对 → 残留分类 → scope ack 或指出偏差）
│    ↓
└─ 未收敛 → 回到落地；各 scope ack 齐 → gate owner 更新聚合 gate → maintainer/operator 拍 merge
```

三层不可混淆：**scope ack**（各 writer 只对自己 scope 表态「我们侧无 blocker」）→
**聚合 gate**（gate/status owner——通常 PR author 或契约载体维护者——聚齐 required acks 后更新状态）→
**不可逆**（maintainer/operator 拍 merge/close）。验收方不宣告全局 gate，落地方不自证收敛。

终止条件：**每个 required scope ack 都绑定 gate 的当前版本锚**。任何一方 pending，聚合 gate 就开着。
版本锚：单 PR 内 = commit SHA（**本文五幕模板均为此场景**）；跨 PR/repo 收敛 = version matrix
（每 artifact 一行：版本 + ack 状态），ack 绑定 matrix 快照而非单一 SHA。

## 各幕话术模板

### 第一幕：意见（review 长文）

```
## <角色> review：<主题>

先说立场：<主方向赞成/反对什么>——防止逐项意见被误读为整体反对。

### <逐项意见，每项：现象 → 为什么是问题 → 建议形状>
（建议形状给 sketch 级别，落笔权留给 owner）

### 流程注记
本 PR 动了 <某方> scope，合入前请确保 <某方> ack。
——<human 账号>（<角色>；起草：<AI 个体署名>）
```

### 第二幕：越权处置（发现对方 PR 动了我方 truth 时）

两种请求，按性质二选一：

```
### 请求撤回：<合同名> 变更
<SHA> 中对 <X> 的修改动的是 <我方 owned> 边界，请从本 PR 撤出、恢复 <基线> 版本。
该收敛由 <我方> writer 主导——你的方案有真实优点，会作为首要候选认真评估，不预设结论。

### 请求转为提案：<变更名>
对 <文档> 的重构动的是 <我方 owned> 状态机，按 writer 制须由我方落地。
技术方向我们初步认可——请以提案形式提出（issue/评论均可），我方裁决后落入权威文档。
```

要点：撤回请求**同时承认对方方案的技术价值**——外交礼仪不是客套，是让对方愿意走程序而不是对抗。

### 第三幕：裁决（对提案的正式回复）

```
### 提案裁决：<ACCEPTED / ACCEPTED_WITH_CHANGES / REJECTED>（附理由）
拒绝理由：<判据下无硬需求支撑 / 成本收益分析>
**收编 N 项**（好想法不浪费：由我方 writer 落入权威文档，誊抄时清洗提案残留语义）
**重启条件**：出现 <硬需求 X/Y/Z> 时本提案作为升级路径重新评审
```

要点：REJECTED 不是句号——收编（吸收局部价值）+ 重启条件（留下未来通道）让拒绝可被接受。

### 第四幕：落地回报（owner 侧）

```
已按<裁决/意见>在 commit <SHA> 完成收口，请复核。
逐项对应如下：
1. <裁决项 1> → <落地方式 + 位置>
2. ...
边界说明：<本次没动什么>（如「X 基线未改动」「未处理 Y 的意见，Z gate 原样保留」）
烦请确认落地是否准确对应；若无新增修正，请 re-ack 本 SHA。
```

要点：**边界说明与逐项对应同等重要**——明说"没动什么"让验收方不必全量扫描。

### 第五幕：验收（意见方回验）

```
@<owner> <SHA> 逐项核对通过：<N> 点全部准确落地，
残留分类干净（活语义残留 0 命中；防御性引用 <M> 处逐项确认为正确清洗），<基线> 未动确认。
<按角色分部的正式确认>
我们侧无剩余 blocker。<gate> 待 <pending 方> 回复 <ACK 词> 后备齐合入条件。
```

要点：这条只声明**自己 scope** 无 blocker——聚合 gate 状态（"备齐合入条件"）由 gate owner 收口宣告。

## 验收 checklist（不信 claim 的机械动作）

1. `git fetch` + checkout 被请求 re-ack 的 SHA（不是分支 HEAD——中间可能又有新 commit）
2. 逐裁决项定位 diff：每项找到落地位置，核对措辞与裁决一致（不是"大概改了"）
3. **grep 残留分类**（防"改了三处漏两处"，也防误杀 provenance）：被裁决清除的术语/字段/枚举全 repo 搜索，
   对**每个命中**分类——**活语义残留**（仍被当作现行合同引用）必须 0；**防御性引用**（「已拒绝、不得恢复」
   类提示、裁决记录、negative guard）可保留但逐项解释。实证：一次验收保留了 8 处防御性引用并判为正确清洗
4. 边界确认：声明"未动"的部分抽查真的未动
5. ack 时复述版本锚 + 逐项结论 + **scope 限定**（只 ack 自己的 scope）；发现偏差则指出具体项，环继续

## 脱敏案例时序（17 条 comment 的骨架）

```
甲 发设计方案 @所有受影响 writer          ← 发起，显式点名
丙 「同意 X；确认前还需冻结 Y 合同」       ← scope 限定表态 + 前置条件
甲 落地 Y → 报 SHA₁ 请再确认
乙 review 长文（先立场后意见 + 术语对照表附录）
甲 落地 → SHA₂
乙 治理意见：请求撤回 A + 请求转提案 B     ← 越权处置（第二幕）
甲 恢复基线 + B 转提案 → SHA₃，请求裁决（三选一表态词）
乙 五部裁决：REJECTED + 3 收编 + 重启条件 + DRI 批准 + 质量修复请求
丙 「方向认可；ACK 前请再补清 3 点」       ← 又一轮 scope 限定 + 前置条件
甲 落地五部裁决 → SHA₄ 请 re-ack
乙 逐项核对 re-ack SHA₄ + 对丙的 3 点表态支持
甲 落地丙的 3 点 → SHA₅ 请 re-ack
乙 逐项核对 ack SHA₅：「我们侧无剩余 blocker，gate 待丙 ACK」
（等丙 BOUNDARY ACK → 合入条件备齐 → 快照交 operator 拍板 merge）
```

观察：每一轮都是「谁的 scope 谁落笔、谁提的意见谁验收、每次表态锚定 SHA」——
这三条不变量让 4 个互不共享上下文的单位在纯异步文本里收敛，没有一次线下会议。

## 本环的失败模式

| 失败 | 症状 | 防御 |
|---|---|---|
| 验收方偷懒信 claim | 偏差滚入下一轮，越滚越贵 | checklist 第 2/3 步是机械动作，不可跳 |
| 验收方宣告全局 gate 关闭 | 抢走 gate owner 聚合权，其他 pending 方被跳过 | scope ack 归 writer，聚合归 gate owner |
| owner 落地时夹带私货 | 验收范围失控 | 边界说明制度（第四幕）+ 验收方抽查 |
| 多方意见交叉打架 | 环变成网，无法收敛 | 每个合同只有一个 writer 裁决；意见方只对自己 scope 表态 |
| ack 语义模糊 | "看过了"算不算 ack？ | 结构化表态词 + 版本锚，二者缺一不算 |
| 落地方等 ack 期间闲置 | 吞吐浪费 | 可并行处理其他 writer 的意见（环可以多路并发，版本锚保证不串线）|
